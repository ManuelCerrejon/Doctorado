01 · PROBLEMA Y OBJETIVO

Reconocimiento local en un microcontrolador

Los sistemas de reconocimiento del habla suelen requerir recursos superiores a los disponibles en microcontroladores.

Los autores estudian la posibilidad de ejecutar reconocimiento de comandos completamente en el dispositivo, evitando depender continuamente de servicios en la nube.

El objetivo es desplegar un modelo compacto y cuantizado sobre Arduino Nano 33 BLE Sense y ampliar el número de comandos que puede reconocer un sistema TinyML.

IMPORTANTE

No es reconocimiento de habla abierta

Aunque el artículo utiliza el término speech recognition, experimentalmente se trata de clasificación de palabras pertenecientes a un vocabulario previamente definido.

El sistema no genera transcripciones libres de longitud variable como Whisper.

COMANDOS COMPLEJOS

Dividir una orden en palabras reconocibles

El sistema no intenta comprender una frase completa mediante un modelo lingüístico.

La orden se divide en pequeños fragmentos reconocidos independientemente.

Cada palabra reconocida activa variables o flags utilizados posteriormente por la lógica del programa.

EJEMPLO CONCEPTUAL

WAKE UP → RED → AND → BLUE → LED

Las diferentes palabras modifican estados internos hasta formar una orden más compleja.

DECISIÓN METODOLÓGICA

Train microphone = Deployment microphone

Los autores capturan el dataset mediante el mismo tipo de micrófono integrado en el dispositivo donde posteriormente ejecutan el sistema.

Esto reduce la diferencia entre las condiciones de recopilación y las de despliegue.

10 · LIMITACIONES

Amenazas a la validez

Un único hablante

Todo el dataset fue recogido utilizando la voz de una persona.

Generalización

Los resultados no demuestran robustez ante hablantes, acentos y voces diferentes.

Edge Impulse

Parte del pipeline funciona como una caja negra externa.

Una única plataforma

La validación se centra en una familia concreta de microcontrolador.

Vocabulario cerrado

El sistema no realiza reconocimiento abierto de secuencias.

Funcionalidad incompleta

Algunas palabras se reconocen, pero su lógica de actuación todavía no está implementada.

PROTOTIPO

Reconocido ≠ comportamiento implementado

BLINK, FAST, SLOW, PLUS, QUICK y TOGGLE pueden ser reconocidos por el sistema, pero la lógica completa asociada a estas órdenes no está implementada en el prototipo publicado.

RELACIÓN CON LA TESIS

Del benchmark al dispositivo real

Esta referencia demuestra que un pipeline acústico completo puede ejecutarse localmente sobre un microcontrolador.

También muestra la importancia de recopilar los datos utilizando el mismo hardware que aparecerá durante el despliegue.

Sin embargo, para una evaluación sostenible más completa sería necesario registrar además memoria, almacenamiento, latencia y energía.

Para la tesis, estas métricas deberían evaluarse conjuntamente con precisión y robustez ante cambios de hablante, ruido y dispositivo.

IDEA DERIVADA PARA LA TESIS

Hardware-in-the-Loop Audio Evaluation

Dataset real ↓ dispositivo objetivo ↓ captura real ↓ modelo optimizado ↓ inferencia local ↓ medir simultáneamente:

accuracy / WER + robustez + RAM + Flash + latencia + energía.
